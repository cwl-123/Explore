# 02 · 训练排障手册

训练出问题时的第一反应不该是"调参"，而是**先定位是哪一类问题**。
这份手册按症状组织，每条给「可能原因 → 怎么验证 → 怎么修」。

---

## 0. 三分钟定位

```
loss 不降？
├── 训练集 loss 也不降 ──────────► ① 学习率/特征/标签 有问题（欠拟合，见 §1）
├── 训练集降，验证集不降 ────────► ② 过拟合（见 §3）
└── 两条都降但很慢 ──────────────► ③ 容量不足 / 特征没信息（见 §4）

AUC 高得不正常（比如 > 0.9）？
└── 先怀疑泄漏，再怀疑自己厉害（见 §5）

离线好，线上差？
└── 五类原因，按顺序排查（见 §7）
```

---

## 1. loss 不降（训练集也降不下去）

| 可能原因 | 怎么验证 | 怎么修 |
|---|---|---|
| 学习率太大（震飞） | loss 前期下降后突然变 NaN 或大幅震荡 | 除以 10，或加 warmup |
| 学习率太小 | 1000 步后 loss 几乎不动 | 乘 10，看前 100 步的下降速度 |
| 特征没标准化 | 数值范围差 1000 倍（价格 vs 小时） | 标准化 / log 变换；树模型不需要 |
| 标签反了 / 全 0 | `y.mean()` 是否接近 0 或 1 | 检查 label 构建逻辑（最常见） |
| 特征全是 ID 类且没 embedding | 模型输入维度很大但都是 one-hot | 换 embedding，或做统计特征 |
| 忘了 `opt.zero_grad()` | 梯度累加，loss 乱跳 | 每个 batch 清零 |

**本仓库对照**：`01_lr_baseline.py` 里 `C=0.5`、`max_iter=200`，如果 loss 停在
0.31 附近不动，先看 `n_iter_` 是否触顶（触顶=没收敛，加大 max_iter）。

---

## 2. loss 震荡 / NaN

- **NaN**：学习率过大、log(0)、除零（CTR 里常见于 `clicks/impressions` 当分母为 0）
- **震荡**：batch 太小 + 学习率大；或数据里有极端值（价格 0.01 元）
- **修**：`clip_grad_norm_`、`log1p`、分母加平滑 `+1e-6`、BatchNorm

---

## 3. 过拟合（训练集好，验证集差）

| 信号 | 判断 |
|---|---|
| train AUC 0.85，valid AUC 0.71 | 典型过拟合，容量远超数据量 |
| train loss 持续降，valid loss 先降后升 | 到拐点就该停 |

修复顺序（从便宜到贵）：

1. **early stopping**（最先做，零成本）
2. 加正则：`weight_decay`、dropout、L2
3. 减容量：embedding 维度、层数、叶子数
4. 加数据 / 加特征（最有效，但最贵）

**本仓库案例**：`04_deepfm.py` 第一版用 `lr=2e-3, weight_decay=1e-5, dropout=0.2`，
valid AUC 在第 3 轮就到顶（0.684），之后一路下滑 —— 因为每人只有 7 条曝光，
1.1 万用户的 embedding 纯靠记忆。
改成 `wd=1e-3, dropout=0.3` 后，valid 涨到 0.708，test 0.722。

> 结论：**ID 越稀疏，正则就要越狠**。这是 CTR 里的铁律。

---

## 4. 欠拟合（训练集和验证集都差）

- 特征没信息量：跑一次 permutation importance，如果所有特征都接近 0，问题在特征不在模型
- 容量不足：加维度/加层/加树（但先确认上一条）
- **最隐蔽的一种**：特征有信息，但被错误的处理方式毁掉了
  （比如把用户 ID 当连续数值喂给树模型）

**本仓库对照**：`02_gbdt.py` 的天花板是 0.795，GBDT 只有 0.718。
差的 0.077 不是模型不行，是「用户 × 商品」的交互信息没有被表达 —— 树模型拿不到，
需要 embedding。这就是"欠拟合"和"模型选错"的区别。

---

## 5. AUC 异常高（先怀疑泄漏）

**判断口径只有一条**：这个特征在**预测那一刻**算得出来吗？

`03_leakage_lab.py` 的实测：

| 特征 | 怎么算的 | AUC | 泄漏程度 |
|---|---|---|---|
| 商品全量 CTR | `groupby('item_id').mean()` 全表 | +0.003 | 温和，最难发现 |
| 用户×商品 全量 CTR | 同上，粒度更细 | **+0.20** | 剧烈，特征≈label |

**为什么粒度越细越危险**：一个商品有 40 条样本，自己那 1 条只占 2.5%，
所以泄漏被稀释；一个「用户×商品」组合往往只有 1 条样本，**特征就是 label 本身**。

**三条自查**：

1. 训练集/测试集**先切分，再算统计量**（顺序错了必泄漏）
2. 任何 `groupby + mean/count` 全表的操作，问一句「这份表里有没有 test 的行」
3. AUC 突然涨 0.1 以上，先当 bug 处理

## 6. AUC 正常，但业务指标不动

| 原因 | 验证方法 | 修法 |
|---|---|---|
| 校准偏了 | 画校准曲线（`calibration_table`） | isotonic / Platt scaling |
| 只优化了排序，没优化价值 | 看 top-k 的 **GMV** 而不只是 CTR | 改目标：eCPM 加权、多目标 |
| 长尾被牺牲 | 分层看 AUC（新用户/新商品单独算） | 加样本权重、冷启动兜底 |
| 生态指标变差 | 看供给端指标（商家曝光分布、退货率） | 加多样性约束、重排规则 |

**记住**：AUC 是"排序对不对"，LogLoss 是"概率准不准"，RPM 是"赚不赚钱"。
三者可以同时背离。

## 7. 离线好，线上差（最常见的线上事故）

按出现频率排序：

1. **训练/服务特征不一致（training-serving skew）**
   离线用 Spark 算，线上用 Go/C++ 算，同一份逻辑两份实现 → 必然分叉。
   验证：同一批样本，离线打分 vs 线上打分，逐特征比对。
2. **特征延迟**：线上拿不到"实时"特征，只能用 T-1 的
3. **样本偏差**：离线只用曝光数据训练，线上要对全量候选打分（曝光偏差 / position bias）
4. **分布漂移**：大促、季节、竞品动作，训练数据的分布已经不成立了
5. **评估口径不一致**：离线 AUC 算的是全体样本，线上考核的是某个流量切片
6. **模型更新滞后**：离线模型一周一更，线上行为已经变了

**工程解法**（这才是你该发挥优势的地方）：

- 特征只写一份逻辑（feature store / 统一 DSL），离线线上共用
- 上线前做「影子打分」：新模型只记录不生效，比对和老模型的分数分布
- 监控：PSI（特征分布漂移）+ 分数分布 + 实时 AUC

## 8. 慢 / 显存爆（资源估算）

**模型显存**（推理）：`参数量 × 精度字节数`

| 场景 | 计算 | 结果 |
|---|---|---|
| 本仓库 DeepFM | 26.9 万参数 × 4B | 1.1 MB |
| 1.2 万用户 × 16 维 embedding | 11525 × 16 × 4B | 0.74 MB |
| 1 亿商品 × 64 维 embedding | 1e8 × 64 × 4B | **25.6 GB** |

**最后一行就是工业界的真问题**：embedding 表放不进单机显存，
必须做**分片（sharding）**、**按热度分层存储**（热 ID 放 GPU，冷 ID 放 CPU/SSD）。

**训练显存** ≈ `参数量 × 4`（参数 + 梯度 + Adam 的 m/v 两个状态），
混合精度可以降到约 2 倍。这就是"7B 模型要 28GB 显存"的来源。

## 9. 一张 checklist（每次训练前过一遍）

- [ ] 标签分布打印了吗？（`y.mean()` 是不是符合预期）
- [ ] 训练/验证是**按时间**切分的吗？
- [ ] 所有统计特征都是**只用历史**算的吗？
- [ ] 数值特征标准化了吗？缺失值怎么填的？
- [ ] 高基数 ID 是 one-hot、统计量、还是 embedding？显存算过吗？
- [ ] baseline 跑了吗？（没跑 baseline 的调参都是耍流氓）
- [ ] test 集是不是只在最后看了一次？
- [ ] 指标之外，看过 top-k 的实际样本吗？（抽样 20 条人工检查）

---

## 10. 一条工程心法

> **离线指标是"能不能上线"的门槛，线上 A/B 才是"该不该上线"的裁判。**

模型上线前，你要能回答三个问题：
1. 这个提升在统计上显著吗？（bootstrap 置信区间）
2. 提升来自哪个切片？（新用户？某类目？）
3. 如果线上不涨，最可能的原因是什么？（提前写好假设）
